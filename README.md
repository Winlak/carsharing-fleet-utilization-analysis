# Утилизация автопарка и баланс спроса

Сравниваю спрос на поездки и доступность машин по районам и времени суток. Ищу места с нехваткой автомобилей и выбираю направления для проверки гипотезы о перебалансировке автопарка.

> **Важно:** весь датасет синтетический, детерминированно создаётся в этом репозитории и не содержит данных Делимобиля или любого другого оператора. Внешние данные не использовались; исходный код распространяется по [MIT License](LICENSE).

## Бизнес-вопрос

Где доступность автомобилей систематически ограничивает бронирование — и из каких зон можно с минимальным риском временно направить 1–3 автомобиля для эксперимента?

Решение должно повысить конверсию без переноса потери спроса в зону-донора. Поэтому кейс отделяет наблюдательные находки от причинных утверждений: приоритеты — это гипотезы, а не обещание эффекта.

## Короткий ответ

За синтетический 2025 год смоделированы **198 990 поездок**, **311 262 поисковые сессии**, 156 автомобилей и 12 условных зон.

| Метрика | Результат | Определение |
|---|---:|---|
| Utilization rate | 26.4% | `in_ride minutes / (in_ride + available minutes)` |
| Available-car minutes | 60.19M | Сумма минут статуса `available` |
| Rides per active car | 0.146 | Поездки на serviceable car-hour |
| Search-to-book conversion | 63.9% | `bookings / searches` |
| Lost demand proxy | 4.4% | Поиски без доступного авто в origin-зоне / все поиски |
| Связь availability → conversion | Spearman ρ = 0.67 | Описательная связь; не причинный вывод |

Самая сильная синтетическая гипотеза: в **будний вечер (17–21)** протестировать перемещение до **3 автомобилей** с **Набережной** в **Деловой квартал**. В получателе lost demand proxy равен 27.5%; это повод для теста, а не оценка инкрементальных поездок.

## Что сделано в SQL и pandas

В `sql/01_zone_hour_supply_demand.sql` календарная сетка гарантирует присутствие всех часов и зон, даже когда в них ноль поездок. Затем CTE агрегируют статусы, поездки и поиски, `LEFT JOIN` соединяет их с сеткой, а `LAG` и 7-дневные оконные средние помогают видеть локальную динамику. Дневная витрина использует `RANK()` и rolling window; городские ставки считаются из компонентов, без «среднего от средних».

В `src/analyze.py` pandas объединяет витрину со справочником зон (`merge(..., validate='many_to_one')`), строит срезы weekday/weekend и month, пересчитывает показатели из числителей и знаменателей, а затем ранжирует получателей и доноров в одинаковом временном окне. Для связи с конверсией используется `starting_available_cars`, зафиксированное **до** поисков текущего часа — исход бронирования не попадает обратно в предиктор.

## Рекомендация и пилот

1. Взять верхние 2–3 пары «донор → получатель» и рандомизировать `зона × окно × дата` внутри weekday/weekend.
2. До запуска закрепить 2 недели pre-period и минимум 4 полные недели пилота; не останавливаться по промежуточным результатам.
3. Primary success: прирост search-to-book conversion не менее 3 п.п. против control и 95% кластерный bootstrap CI для разницы, исключающий ноль; параллельно — абсолютное число бронирований.
4. Guardrails: в зоне-доноре lost demand proxy растёт не более чем на 1 п.п. по верхней границе 95% CI; городской объём поездок не снижается более чем на 2%; доля relocating/charging-часов не растёт необъяснимо.
5. Анализировать intention-to-treat и различие pre/post внутри страт. Не заявлять причинность при нарушении рандомизации или одновременной смене цен/промо.

Подробная методика и ограничения — в [отчёте](docs/analysis_report.md).

## Воспроизводимость

Требования зафиксированы в [requirements.lock](requirements.lock). Полный прогон создаёт локальные raw CSV, запускает SQL-витрины в DuckDB, анализ в pandas, графики, Markdown-отчёт и исполняет notebook-копию. Большие raw- и mart-CSV, PNG-рендеры и исполненная notebook-копия не коммитятся: их байты зависят от графической и kernel-среды. Сохранённые отчёты и визуализации — автономные HTML и исходные JSON в `artifacts/`.

```bash
git clone https://github.com/Winlak/carsharing-fleet-utilization-analysis.git
cd carsharing-fleet-utilization-analysis
make install
make lint
make test
make reproduce
make reproduce-check
```

После `make reproduce` ключевые результаты находятся в `outputs/`, отчёт — в `docs/`, проверка качества — в `data/processed/data_quality_report.md`, а исполненный notebook — в `work/fleet_utilization_analysis.executed.ipynb`. `make reproduce-check` дополнительно подтверждает, что после полного pipeline Git-дерево остаётся чистым. HTML-артефакты уже лежат в `artifacts/` с сохранёнными результатами; их канонические входы — `artifacts/*_artifact.json`.

## Ограничения

- Синтетическая модель задаёт сезонность, спрос и вероятность бронирования; числа демонстрируют метод, а не рынок.
- Почасовой статус округляет внутрисчасовую поездку до status-hour, поэтому это не телематический расчёт до минуты.
- `lost demand proxy` — наблюдаемая нижняя граница; он не учитывает пользователей, не начавших поиск.
- Для production-решения нужны фактические ETA, радиус поиска, цена, отмены, парковочные ограничения, стоимость релокаций и выручка.
